# ADR-0003: 宣言していないメタデータキーでの絞り込みを例外で拒否する

- ステータス: 採用
- 日付: 2026-11-02
- 関連: M4 TASK-001、要件 R5（[`plans/search-filtering-requirements.md`](../work/plans/search-filtering-requirements.md)）

## コンテキスト

`SearchRequest#filters` は公開 API として存在するが、`LuceneFullTextSearcher` と
`LuceneVectorSearcher` はこの値を読まない。利用者が絞り込み条件を指定しても、
例外も警告もないまま絞り込まれていない結果が返る。

TASK-003 と TASK-004 で、Namespace 設定に索引対象メタデータキーを宣言する仕組みを導入する。
宣言したキーだけが Lucene のフィールドとして書き込まれ、宣言していないキーは索引に存在しない。

ここで、宣言していないキーが絞り込み条件に現れた場合の挙動を決める必要がある。
Lucene の `TermQuery` は存在しないフィールドに対して 0 件を返すため、何も手を打たなければ
「そのキーを含む条件は必ず不一致」となり、利用者には理由のわからない空の結果が返る。

同じ構造の問題が値の型にもある。要件 R1 で索引へ書けるのは文字列と文字列配列に限ると定めたが、
`Document.metadata` の値の型は `Object` のため、数値・真偽値・入れ子の `Map` も渡せる。
宣言したキーであっても、型が合わなければ索引に入らない。

要件 R5 は、どちらの場合も黙って無視することを認めていない。

### 後方互換の制約

現状、`filters` に任意のキーを渡しているコードは例外なく動作している。
絞り込みが効いていないだけで、呼び出し自体は成功する。
ここで一律に例外を投げるようにすると、既存の呼び出しがすべて失敗する。

## 検討した選択肢

| # | 方式 | 設定漏れの検出 | 結果の正しさ | 採用 |
| --- | --- | --- | --- | --- |
| 1 | **宣言外キーを例外で拒否する** | 即時 | 誤った結果を返さない | ✅ |
| 2 | 事後フィルターへ退避する | 検出しない | `limit` 不足で件数が欠ける | ✕ |
| 3 | 警告ログを出して条件を捨てる | ログのみ | 絞り込まれていない結果を返す | ✕ |
| 4 | Lucene の素の挙動に任せる | 検出しない | 理由のわからない 0 件を返す | ✕ |

### 各選択肢を採らなかった理由

選択肢 2 は、宣言外のキーを取得後の判定へ回す案である。
絞り込み自体は効くが、`limit` 件を取得してから捨てるため、必要な件数が揃わない。
利用者は欠落に気づけず、ページングも壊れる。
要件 R5 が解消しようとしている「黙って期待と違う結果を返す」状態が形を変えて残る。

選択肢 3 は、ログが出るという点で選択肢 4 より良い。
ただしライブラリとして組み込まれる場合、ログの監視は利用側の運用に依存する。
権限での絞り込みに使われることを考えると、条件が落ちたまま結果が返るのは危険である。

選択肢 4 は実装が不要だが、利用者から見ると設定漏れと「本当に該当なし」を区別できない。

## 決定

選択肢 1 を採る。あわせて、機能を使っていない Namespace の後方互換を保つ。

### 宣言外キーの扱い

索引対象キーを 1 つ以上宣言している Namespace では、宣言外のキーが絞り込み条件に現れた時点で
`IllegalArgumentException` を投げる。例外は検索を実行する前、クエリを組み立てる段階で投げる。
メッセージには、問題のキーと、その Namespace で宣言済みのキー一覧を含める。

索引対象キーを 1 つも宣言していない Namespace でも、絞り込み条件が指定されていれば同じく例外で失敗させる。
当初はここだけ従来どおり無視して `WARN` ログを残す案を採ったが、後述のとおり撤回した。

### 値の型の扱い

索引の書き込み時、宣言したキーの値が文字列でも文字列配列でもない場合は
`IllegalArgumentException` を投げる。検索時ではなく索引時に止めるのは、
索引へ入っていない値は後から検索で救えないためである。
要件 R9 が埋め込みモデルの不一致を索引前に止めるのと同じ考え方を取る。

### FacetFilter の去就

`FacetFilter` は削除せず残す。TASK-022 で実装する「取得後に判定する介入点」の既定実装の素材として使う。
残すにあたり、事後フィルターであること、`limit` を増やさなければ件数が欠けることを Javadoc に明記する。

## 影響範囲

### コード

- `LuceneDocumentMapper` に、宣言キーの値の型検証を追加する（TASK-004）
- フィルター式から Lucene クエリを組み立てる箇所に、宣言済みキーの照合を追加する（TASK-005）
- `FacetFilter` の Javadoc を更新する（TASK-009）

### 互換性

- 良い: 設定漏れと条件の指定ミスが、誤った結果ではなく例外として即座に表に出る
- 良い: 絞り込みを指定した検索が、絞り込まれていない結果を返すことがない
- 悪い: これまで `filters` を渡していた呼び出しは、索引対象キーを宣言するまで例外になる。
  ただし 1.0.0 の `filters` は完全に無視されており絞り込みは働いていなかったため、
  変わるのは呼び出しの成否だけで、返っていた結果の中身は変わらない
- 中立: 絞り込みを指定しない呼び出しは影響を受けない
- 悪い: 一括取り込みの途中で型の合わない値に当たると、その文書で失敗して取り込みが止まる。
  取り込み前に値を整える手間が利用者に生じる
- 中立: `FacetFilter` は残るが、TASK-022 まで `main` から呼ばれない状態が続く

## 訂正（2026-11-02）

当初の決定では、索引対象キーを 1 つも宣言していない Namespace に限り、
後方互換のため `filters` を無視して `WARN` ログを残すこととしていた。
自動のセキュリティレビューで、認可バイパスにあたるとの指摘を受けて撤回した。

撤回の理由は 2 つある。
1 つは、この絞り込みの主な用途が閲覧権限による候補の限定であり、
設定漏れのときに返るのが「利用者に見せてはいけない文書を含む結果」になること。
もう 1 つは、ログがライブラリ利用側の運用に依存し、気づける保証がないことである。
ADR として「黙って無視することは認めない」と書きながら、
ログだけで通す扱いを残していたのは判断の誤りだった。

後方互換の懸念は、実際には小さい。
1.0.0 の `filters` は検索エンジンまで届いておらず絞り込みは働いていないため、
例外化で変わるのは呼び出しの成否だけで、それまで返っていた結果の中身は変わらない。
